## What PendingAccess Is For

PendingAccess exists to handle exactly one specific scenario:

> **Someone successfully authenticates with Keycloak (correct username and password), but Django has no matching user account for them.**

This is NOT about wrong passwords. Wrong passwords are rejected entirely by Keycloak itself, before Django is ever involved.

---
## The Critical Distinction — Authentication vs Authorization

This is the concept you must understand clearly:
```
AUTHENTICATION = "Are you who you say you are?"
                  → Handled by Keycloak
                  → Checks username + password

AUTHORIZATION  = "Do you have permission to use THIS system?"
                  → Handled by Django
                  → Checks if a CustomUser profile exists
```

PendingAccess deals only with the second one. A person can pass authentication (Keycloak knows them) but fail authorization (Django has no profile for them).---

## Scenario 1 — Wrong Password (Does NOT create PendingAccess)```
User types wrong password on Keycloak's login page
        ↓
Keycloak checks against its own user store
        ↓
Keycloak rejects immediately — "invalid credentials"
        ↓
Browser never even reaches Django
        ↓
NO PendingAccess record created
NO Django code runs at all
```

Keycloak handles this entirely on its own. If you enabled Keycloak's Brute Force Detection (which we discussed in Phase 5), Keycloak also locks the account after 5 failures — again, entirely inside Keycloak, never touching Django.---

## Scenario 2 — Correct Keycloak Login, No Django Profile (Creates PendingAccess)```
User types CORRECT password for a Keycloak account
        ↓
Keycloak verifies it successfully ✓
        ↓
Keycloak issues a token and redirects to:
http://localhost:8000/oidc/callback/?code=XXXX
        ↓
Django's GovAssetOIDCBackend.filter_users_by_claims() runs
        ↓
Searches CustomUser by keycloak_id → not found
Searches CustomUser by username → not found
        ↓
Because nothing was found, create_user() is called
        ↓
create_user() does NOT auto-create the user (security decision)
Instead it creates a PendingAccess record:
    username, email, full_name, keycloak_id, status='PENDING'
        ↓
Returns None → login is BLOCKED
        ↓
User sees: "Previous login attempt failed. Please try signing in again."
```

This is exactly what happened in our earlier `ghost_user` test — remember the logs showed:

```
WARNING ... OIDC: No Django user found for Keycloak user: ghost_user
WARNING ... OIDC: No Django user found... Access blocked.
```

That warning is the exact moment a PendingAccess record gets created.

---

## Does This Apply to Mobile / API Login?

**No.** Mobile login (`POST /api/auth/login/`) never touches `GovAssetOIDCBackend` at all. It calls Django's `authenticate()` directly against the Django database. If the username does not exist in Django, it simply returns "Invalid username or password" — no PendingAccess record, because the OIDC flow was never involved.

PendingAccess is **strictly a web SSO concept**.

---

## What Happens After a PendingAccess Record Is Created

The Super Admin or Ministry Admin reviews it:

```
Login as superadmin or moh_admin
        ↓
Go to Pending Access page
        ↓
See: username, full name, email, keycloak_id, status=PENDING, timestamp
        ↓
Click "Review"
        ↓
Two choices:
    APPROVE → admin goes to User Management and creates
              a Django profile with proper role + ministry_schema
              using the SAME username so next login matches
    REJECT  → status changes to REJECTED
              user remains permanently blocked
              (filter_users_by_claims still finds nothing,
               create_user still returns None forever)
```

## Summary Table

| Scenario | Where it's checked | PendingAccess created? |
|---|---|---|
| Wrong password on Keycloak page | Keycloak itself | ❌ No |
| Correct Keycloak password, no Django profile | Django's OIDC backend | ✅ Yes |
| Correct Keycloak password, Django profile exists | Django's OIDC backend | ❌ No — normal login |
| Wrong username/password on mobile API login | Django `authenticate()` directly | ❌ No |
| 5 failed Keycloak attempts (if Brute Force Detection enabled) | Keycloak itself | ❌ No — Keycloak locks account |

QUESTON

My recommendation: Leave it exactly as it is. If your supervisor ever asks "why does a Ministry Admin see pending requests for other ministries," your honest answer is:

"At the point a login is blocked, the system doesn't yet know which ministry the person belongs to — they have no profile. We deliberately keep that triage decision visible to any reviewing admin so nobody falls through the cracks unreviewed, since the alternative — hiding it — risks a legitimate user being permanently invisible to anyone."

That's a defensible, intentional design answer, not a confession of a bug.
